# 분석 화면 및 공통 로딩 성능 개선

작성일: 2026-09-08 · 기준 코드: `c7ea7ece` · 작업 브랜치: `codex/loading-performance-20260908`

상태: **로컬 구현·검증 완료.** 2026-09-09 사용자 요청에 따라 백엔드와 프런트엔드를 순서대로 배포한다. 최종 배포 상태는 각 PR, main의 Test and Deploy 실행 및 운영 `build-info.json`으로 확인한다. 아래 빌드 크기와 SQL 수는 실제 운영 응답시간 개선률을 뜻하지 않는다.

## 관찰과 원인

운영 `/analysis`를 로그인된 Chrome에서 읽기 전용으로 관찰했다. 기존 화면은 생산 요약과 현장 기록을 병렬로 요청했지만, 생산 요약에 전체 종합현황판 API를 사용했다. 이 API는 품질·에너지·재고·금형·날씨 등 분석의 첫 생산 수치에 필요하지 않은 자료까지 처리한 후 응답했다.

- 전체 현황판 API의 관찰 응답시간: 3.92, 4.18, 3.89, 4.65, 4.02초.
- 현장 기록 API: 대부분 0.32~0.61초, 한 번은 3.56초.
- 문서 DOMContentLoaded/Load: 약 1.38/1.39초. 이는 로그인 후 생산 수치가 준비된 시각과 다르다.
- `/user/me/`의 일시적인 502 후 기존 5초 재시도와 정상 응답을 관찰했다. 서버 로그로 원인은 확인하지 않았으며, 이번 변경으로 해결됐다고 판단하지 않는다.
- 이후 자동 갱신을 더 관찰하자 전체 현황판 API에서 17.24/17.38초, 현장 기록에서 7.20초인 응답도 있었다. 위 3.9~4.7초는 초기 표본이며 상한이 아니다. 간헐적인 서버 지연의 별도 추적이 필요하다.

캐시를 강제로 비우거나 네트워크를 고정한 반복 실험이 아니므로 위 숫자는 병목을 찾기 위한 관찰값이다. 인증 동작과 Render 설정은 변경하지 않았다.

## 구현

### 먼저 필요한 자료만 조회

`backend/production/overview_board.py`와 `views.py`에 기존 읽기 API의 `scope=production`을 추가했다. 응답 스키마는 `production-overview.v1`이다. 기존 생산 계산, 업무일, 설비 상태와 원천 경고를 그대로 사용하고, 부가 자료 조회 전에 반환한다. 기본값 `full`은 기존 종합현황판 응답을 유지한다. 잘못된 scope는 400이며 `no-store`도 유지한다.

`frontend/src/domains/analysis/`는 생산·MES 원천과 현장 기록을 먼저 표시한다. 품질·에너지·재고·금형·날씨 원천 상태는 사용자가 펼칠 때 기존 전체 API로 별도 조회한다. 펼친 동안만 자동 갱신한다. 과거일 부가 자료에 최근 스냅샷이 섞일 수 있다는 안내는 유지한다.

날짜 변경이나 페이지 이탈 시 React Query의 취소 신호를 HTTP 요청에 전달한다. 부가 조회 실패는 생산 요약을 가리지 않는다. 새로고침 실패 시 기존 수량은 마지막 수신값으로 표시하고 달성률·우선 판정은 보류한다. 빈 자료나 실패를 데모 데이터 또는 0으로 대체하지 않는다.

### 반복 SQL 및 큰 자료 읽기 축소

- `ai_retrievers.py`: 설비별 하루/최근 구간 카운터를 함께 읽는다. 설비당 5번이던 해당 부분의 SQL을 설비 수와 관계없이 총 2번으로 줄였다. 이전 기준값과 구간 샘플을 조회한 뒤 기존 누적 카운터 함수를 사용한다.
- `injection/mes_service.py`: 조회 구간 이전의 전체 로그를 Python 객체로 만들지 않고, 설비별 유효 기준 레코드 ID만 SQL로 고른다. 최신 시각·카운터·톤수도 필요한 필드만 읽고, 17대 톤수의 개별 조회를 하나로 묶었다.
- `machining_reconciliation.py`: 일별 MES 대사에서 사용하지 않는 큰 `raw_payload` JSON을 읽지 않는다.
- 생산 대시보드와 MES 모니터링은 동일한 전 설비 요청을 같은 React Query 키로 공유한다. 30초 이내 재진입과 동시 요청을 재사용하되 업무일·현재/과거 구간·개별 현장 설비의 캐시는 분리한다. 명시적 갱신은 이 재사용 시간을 우회한다.

17대, 합성 로그 5,440행의 전후 비교에서 MES 행렬 전체 응답이 같았다. SQL은 21→5회, 생성한 카운터 모델 객체는 5,441→357개였다. 단일 설비도 전체 응답이 같고 SQL은 22→5회였다. 이는 SQLite 합성 실험이며 운영 PostgreSQL의 실행 계획이나 소요시간을 대신하지 않는다.

### 첫 화면 자바스크립트 분리

분석 차트는 생산 수치가 준비된 뒤 불러온다. 차트 공간과 기존 표현은 유지하고, 차트 파일 로딩 실패 시 수치를 계속 볼 수 있도록 안내한다. 생산 API 모듈의 데모 구현은 실제로 필요한 분기에서만, Excel 파서는 파일을 읽을 때만 불러온다.

같은 Vite 설정과 빈 환경 설정 디렉터리로 기준 코드와 변경 코드를 각각 빌드했다. 아래는 앱 진입점과 각 페이지의 **정적 JS 의존 파일을 한 번씩 합산한 gzip 바이트**이며 CSS·이미지·지연 청크는 제외했다. 차트 지연 로딩은 최종 차트 표시까지의 총 다운로드를 없애는 것이 아니다.

| 페이지 | 변경 전 | 변경 후 | 감소 |
| --- | ---: | ---: | ---: |
| 분석 `/analysis` | 316,247 | 211,151 | 33.2% |
| 생산 대시보드 | 416,583 | 252,932 | 39.3% |
| MES 모니터링 | 390,374 | 226,765 | 41.9% |
| 종합현황판 | 340,812 | 340,810 | 사실상 동일 |
| 품질 분석 | 344,581 | 344,548 | 사실상 동일 |
| 원자재 관리 | 216,553 | 216,522 | 사실상 동일 |
| 재고 현황 | 199,953 | 199,934 | 사실상 동일 |

주요 7개 페이지의 번들 경로를 비교했다. 기존 페이지 단위 분할은 이미 적용되어 있었다. 원자재의 메타데이터 우선 조회도 현재 코드에 존재해 재구현하지 않았다. 모든 페이지의 운영 응답시간이 개선됐다는 의미는 아니다.

## 검증

- 격리 SQLite에서 백엔드 회귀 테스트 **113개 통과**: 현황판, 생산 수량·배분·누적 카운터, 사출 행렬/롤업/에너지, 조립 수기 대사, AI 결정론적 답변. 최종 음수 샘플 보강 후 성능 테스트 6개 재실행 통과.
- 프런트엔드 전체 Node 테스트 **164개 통과**. 실제 QueryClient로 동시 요청 합치기, 30초 만료, 날짜·설비 분리, 명시적 무효화를 검증한다.
- 번들로 실행한 추가 검사 **19개 그룹 통과**: 데모/Excel 지연 로딩 및 실제 합성 Excel 파싱, 응답 스키마·날짜·누락/0 구분, 한중 언어, 취소 전파, 데모 대체 금지. 외부 요청은 모의 처리했다.
- 기준·변경 MES 전체 응답 비교 통과. 임의 카운터 데이터 100개 사례/500개 설비 구간도 기존 계산과 동일했다.
- TypeScript, 변경 후 Vite 프로덕션 빌드, 레거시 CSS 빌드, `git diff --check` 통과. ESLint 오류 0, 기존 경고 31개 유지. 큰 청크에 대한 Vite 안내는 남아 있다.
- 실제 분석 컴포넌트에 합성 데이터를 연결한 Chrome 한국어·중국어 화면에서 배치와 가로 넘침, 중복 ID를 확인했다. 최초 생산/현장 요청은 각각 1회, 부가 요청은 0회였다. 펼치기 후 5초 지연 및 실패에도 생산 수치는 유지됐다. 갱신 실패 시 마지막 수신값 안내와 판정 보류도 확인했다.

검증은 프로젝트 `.env`나 운영 DB를 사용하지 않았다. UI 미리보기에는 합성 데이터 표시를 넣고 API 프록시를 차단했다. 모바일 실기기와 운영 PostgreSQL 실행 계획은 이번 검증에 포함하지 않았다.

## 배포와 후속 확인

백엔드 변경은 [PR #41](https://github.com/ssoe94/wj_reporting/pull/41)로 분리했다. 신규 `scope=production`을 제공하는 백엔드를 먼저 반영하고 정상 응답을 확인한 뒤 프런트엔드를 반영한다. 데이터베이스 마이그레이션은 없다.

배포 후 같은 날짜로 신규 생산 범위 API와 기존 전체 API의 수치·설비·원천 시각을 비교하고, 첫 진입/재진입의 실제 API 시간과 화면 수치 표시 시점을 다시 측정한다. 로그인 확인 502는 Render 요청/프로세스 로그와 함께 원인을 확인한다. PostgreSQL에서 기준값 서브쿼리의 실행 계획도 확인한 후 추가 인덱스나 서버 설정 변경의 필요성을 판단한다.
