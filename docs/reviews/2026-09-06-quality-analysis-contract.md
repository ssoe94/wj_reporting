# 품질 신고 분석 계약

이 문서는 공개 코드와 합성 테스트에 근거한다. 운영 원장이나 실제 업무 수치는 포함하지 않는다.

## 목적과 원천

`GET /api/quality/analysis/`는 확정 저장된 `QualityReport`를 기간·공정·명시 설비 범위로 집계한다. 신고가 반복되는 유형과 품번, 자료 보완이 필요한 지점을 찾는 조회용 API다. `IsAuthenticated`와 기존 `QualityReadPermission`을 적용하며 원장·분류·중복후보를 변경하지 않는다.

실제 원천 필드는 `backend/quality/models.py`의 `QualityReport.report_dt`, `section`, `part_no`, `phenomenon`, `defect_qty`, `inspection_qty`, `lot_qty`, `judgement`다. 모델에 설비 번호나 검증된 불량 유형 코드가 독립 필드로 존재하지 않는다. 기존 저장된 `defect_rate`는 문자열이며 집계에 사용하지 않는다.

설비는 기존 `QualityReportSerializer.get_source_import`와 동일한 원천 우선순위로 승인된 가져오기 행의 `occurrence_location`, 해당 행이 없으면 `excel_source.occurrence_location`을 읽는다. `IMM01`, `1호기`, `1号机`, `机台1`, `850T-1`처럼 명시된 1~17 번호만 인정한다. 여러 설비가 적혀 있거나 공정명만 있는 경우 `unknown`이다. 오늘 생산계획이나 품번 접두어로 과거 발생 설비를 추정하지 않는다. 이것은 기록된 발생 위치이지 원인 설비를 검증한 결과가 아니다.

## 조회 범위

| 파라미터 | 계약 |
|---|---|
| `start_date`, `end_date` | 엄격한 `YYYY-MM-DD`, 양끝 날짜 포함. 기본 최근 30일, 미래·역순·366일 초과는 400 |
| `section` | 생략 시 전체. `LQC_INJ`, `LQC_ASM`, `IQC`, `OQC`, `CS` |
| `machine_number` | 생략 시 전체. 문자열 `1`~`17` 또는 `unknown`; 빈 값·`01`·`1.0` 등 거절 |

날짜는 **`report_dt`의 Asia/Shanghai 달력 날짜, 00:00~다음날 00:00**다. 사출 MES의 08:00 영업일과 다르다. `created_at` 업로드일이나 현재 생산계획일로 치환하지 않는다. `options.machines`만 기간·공정 범위에서 설비 선택 전의 선택지와 건수를 제공한다. 나머지 집계·최신 시각·검토 후보는 선택 설비까지 적용한 동일 범위다.

원천은 한 번의 필요한 필드 조회와 선택적 one-to-one 조인으로 읽고 서버에서 순회 집계한다. 브라우저에 원장 전체나 사진·원본 파일정보·자유서술을 전송하지 않는다. 기간·공정 범위의 원천이 50,000건을 넘으면 범위를 좁히라는 400을 반환한다. 잘린 원천으로 전체 통계를 만들지 않는다. DB·마이그레이션·수집기는 변경하지 않는다.

## 지표 정의와 0/null

| 지표 | 해석 |
|---|---|
| `report_count` | 선택 범위의 저장 신고 행 수. 독립 사건 수나 불량 제품 수와 같다고 가정하지 않음 |
| `reported_defect_qty` | 유효한 0 이상의 정수 `defect_qty`가 기입된 행의 합. 유효 기입 행이 없으면 `null` |
| `defect_quantity_record_count` | 불량 수량이 유효하게 기입된 신고 건수. 수량 합계의 관측 범위 |
| `recorded_inspection_qty` | 유효하게 기입된 검사 수량의 합. 동일 LOT 재검사나 반복 신고의 중복 분모 가능 |
| `paired_quantity_record_count` | 불량·검사 수량이 모두 유효한 신고 건수. 두 값의 모집단 일치를 인증하지 않음 |
| `zero_defect_report_count` | 불량 수량 0을 명시적으로 기입한 신고 건수 |

아무 신고가 없는 날의 신고 건수는 0, 불량 수량은 `null`이다. 신고는 있지만 수량을 쓰지 않은 경우도 수량은 `null`이다. 명시적으로 0을 기입한 신고는 0으로 유지한다. 일부만 수량을 기입한 경우 합계는 그 기입 범위의 합이고, 기입 건수와 누락 건수를 함께 반환한다.

품질 원장은 발생 문제 중심 기록이며 정상 검사 전체 모집단이 확보되었다고 볼 수 없다. **전체 공장 불량률·양품률·설비별 불량률을 반환하지 않는다.** 기록된 검사 수량을 모두 더하더라도 고유 검사 분모나 생산 분모로 간주하지 않는다. 불량 수량이 검사 수량보다 큰 행은 `inconsistent_quantity_count`로 알리되 신고된 불량 수량 자체는 삭제하지 않는다. 잘못된 음수·비정수 값만 수량 합에서 제외한다.

## 응답 구조

버전은 `quality-analysis.v1`이다. `status`는 `no_records`, `ok`, `partial`이며 `partial`은 집계가 잘렸다는 의미가 아니라 기입 누락·모순·분류 한계·중복 검토 후보가 있다는 의미다. 모든 성공 응답은 선택 범위 원천을 끝까지 집계한다.

- `filters`: 적용 날짜·공정·설비, `timezone`, `date_basis=report_dt_calendar_day`.
- `summary`: 신고 건수, 수량 합계와 기입 건수, 0 기입 건수, 마지막 신고 시각.
- `trend`: 범위 안 모든 날짜의 신고 건수·수량 합계·수량 기입 건수. 무신고 날짜도 포함한다.
- `pareto`: 신고 건수 내림차순 유형, 한중 라벨, 신고 수량, 전체 신고 대비 비중, 누적 비중, 대표 원장 ID.
- `concentrations.machines/parts/sections`: 신고 건수 상위 20개 `items`, 전체 그룹 수 `total_group_count`, 나머지 신고 건수 `other_report_count`. 비중 분모는 상위 20개의 합이 아니라 전체 선택 신고 건수다.
- `data_quality`: 수량·검사·품번·현상 누락, 수량 이상·모순, 유형 미분류·복합 유형, 미지정 설비, 중복후보 건수.
- `options`: 공정 선택지와 기간·공정 범위의 설비 선택지. 선택 설비와의 범위 차이를 `scope`로 명시한다.
- `freshness`: 응답 생성 시각, 선택 범위 마지막 신고·수정 시각, `refresh_policy=event_driven`. 과거 신고가 오래되었다는 이유만으로 수집 장애를 단정하지 않는다.
- `source`: 모델·분류 사전 버전·원천 제한·대표 ID 제한. `warnings`, `limitations`, `calculation_basis`도 반환한다.

유형은 `quality.daily_attention._canonical_problem_types`와 버전이 있는 `injection_terminology`를 재사용한다. 한 신고가 여러 유형에 일치하면 `multiple` 한 버킷으로 묶는다. 현상 미기입과 미분류도 별도 버킷이다. 따라서 유형별 신고 건수 합은 `summary.report_count`, 유형별 기입 수량 합은 전체 기입 수량 합과 일치한다. 이는 사전 기반 현상 분류이며 근본 원인 판정이 아니다.

중복후보는 동일 달력일·공정·정규화된 정확 품번·현상·원본 발생 위치·수량·판정이 같은 2건 이상 그룹이다. 품번 또는 현상이 없으면 후보키를 만들지 않는다. 동일 특성의 독립 사건도 있을 수 있으므로 자동 제거하지 않는다. 대표 ID는 각 그룹 최대 5개이며 전체 원장 목록으로 표현하지 않는다. 원본 확인은 기존 권한 있는 `/api/quality/reports/{id}/`를 재사용한다.

## 검증

`backend/quality/test_analysis.py`의 합성 테스트는 0/미기입/무신고 구분, 부분 수량 커버리지, 검사보다 큰 불량 수량, 유형 중복 합산 방지, 중복후보 유지, 설비 범위·모호한 위치, 상위 20개 분모와 대표 ID 제한, 날짜·필터 검증, 원천 상한 거절, Shanghai 자정 경계, 가져오기 원천 우선순위, 단일 SQL 조회, 품질 읽기 권한을 확인한다.

운영 설정을 로드하지 않는 별도 SQLite 메모리 설정에서 테스트한다. 네트워크 요청과 `.env` 로드는 차단하고 모든 입력은 합성 자료다. 마이그레이션 파일을 만들거나 운영 DB에 접속하지 않는다.

## 다음 수집 우선순위

1. **검사 이벤트와 사건 식별자:** `inspection_event_id`, `quality_incident_id`, 원본 중복·재검사·재발 관계. 같은 LOT의 반복 신고를 생산량이나 검사 분모로 중복 계산하지 않도록 한다.
2. **구조화된 발생 위치:** 공정, 설비 ID, 라인, 제품 LOT, 생산 작업/교대 ID, 발견 위치와 원인 위치를 각각 저장한다. 사람이 확인한 연결과 자동 제안을 구분한다.
3. **검사 모집단:** 고유 검사 수량, 불량 개체 수, 샘플링 방식, 전수/표본/재검사 구분, 단위, 검사 시작·종료시각. 정상 검사 0불량도 같은 규칙으로 기록해야 비율을 설계할 수 있다.
4. **현상과 조치의 구조화:** 현상 코드·수량, 복수 유형의 동일 개체 중복 여부, 원인 검증 상태, 조치 담당자·완료시각·재발 확인을 기록한다. 현상 키워드를 확인된 원인이나 처리 완료로 바꾸지 않는다.
5. **원천 품질 추적:** 수기/가져오기 원천 ID, 입력자·수정 감사, 필드별 결측 원인, 지연 입력, 중복 검토 결과를 저장한다. 대시보드에서 누락률과 조치 후 재발을 추적할 수 있는 기반이다.

이 수집 단계는 후속 모델·폼·검증 설계 대상이며, 현재 변경이 새 필드를 수집하기 시작했다고 주장하지 않는다.
