# 생산계획 · MES 작업 대사 — 조회 전용 구현

## 목적과 승인 범위

2026-10-08 대화에서 검토한 수정 방향에 따라 조회 전용 패널을 구현했다.
계획 일치를 현재 생산 확정으로 표시하지 않고, 동일 품번의 여러 작업과 계획 LOT를 확인 대상으로 남긴다.
이 문서는 로컬 구현 기록이며 배포·현장 인수·실제 MES 계약 검증 완료를 의미하지 않는다.

## 구현

- 브랜치: `codex/mes-task-reconciliation-20261008`, 기준 커밋 `9039735f`.
- `GET /api/production/mes-task-reconciliation/?business_date=YYYY-MM-DD`.
- `/production` 하단에 독립 컴포넌트로 표시. 다른 대시보드 원천이 실패해도 패널을 조회할 수 있다.
- 현재 `/production` 화면의 로그인 조건 및 생산계획 조회 규칙에 맞춰 활성 로그인 사용자가 조회한다. 기존 일부 익명 dashboard API의 공개 범위를 새 작업 상세에 확대하지 않는다.
- API 응답은 호기 1~17, 양일 계획, 열린 MES 작업, 별도 형합 관측, 설비 미연결 작업, 조회 시각과 보류 이유를 포함한다.
- 작업 변경 API·마이그레이션·쓰기 버튼은 이번 구현에 포함되지 않는다.

## 판정 계약

| 코드 | 의미 |
| --- | --- |
| `plan_match` | 호기·품번이 선택일 계획에 있음. 실제 생산 중이거나 특정 계획 LOT에 연결됐다는 확정이 아님 |
| `next_plan_match` | 다음 날짜 계획에 있음 |
| `task_link_review` | 같은 품번의 열린 작업이 여러 개거나 선택일 계획 LOT/행이 여러 개임 |
| `pause_review` | 양일 호기 계획이 있고, 해당 품번이 양쪽 모두에 없으며 MES 상태가 실행 중임. 현장 확인을 위한 후보 |
| `start_needed` | 선택일 계획의 열린 작업은 있으나 실행 중 작업이 없음 |
| `no_open_task` | 완전한 조회 범위에서 계획에 맞는 열린 작업이 없음. 工单 자체가 없다는 뜻이 아님 |
| `outside_plan` | 양일 계획 밖의 대기·정지 작업 |
| `unknown` | 조회·계획·작업 식별 근거가 불완전하거나 현재 MES 상태를 다른 날짜의 계획과 비교함 |
| `unmapped` | 작업 설비를 한 호기에 연결할 수 없음 |

동시생산은 기존 `build_cavity_plan_groups`와 `ProductionPartCavity.cavity_group`을 사용한다.
같은 호기·같은 날짜 안에서만 묶고 `sequence`만 같다고 묶지 않는다.
캐비티 설정은 현재 기준정보이며 과거 생산 구간의 확정 기록이 아니다.

개시 후 14일 이상, 명시된 동일 단위의 보고 수량 충족, 보고 0은 참고 사유다.
어느 경우에도 완공·취소를 판정하지 않는다. 14일 기본값은 선택적 Django 설정
`MES_TASK_OLD_OPEN_DAYS`로 바꿀 수 있으며 환경 파일이나 배포 설정을 수정하지 않았다.

## 날짜·신뢰도·호출

- 업무일은 Asia/Shanghai 08:00~다음 날 08:00. 다음 비교 날짜는 다음 24시간 업무일 구간이다.
  공장 휴무일을 추정하거나 다음 계획이 존재하는 날짜로 건너뛰지 않는다.
- 과거·미래 날짜를 조회해도 MES 목록은 현재 상태다. 조치 판정을 보류한다.
- 한 호기의 양일 계획이 부족하면 계획 밖 작업의 조치 판정을 보류한다.
- 부분 페이지, 중복 ID, 조회 중 total 변경, 미지원 식별 필드, 설비 미연결 작업이 있으면
  작업 부재 및 조치 판정을 보류한다. 원천 실패를 정상 0건으로 표시하지 않는다.
- 형합은 저장된 해당 업무일의 최근 최대 10,000개 관측에서 인접 시각의 양의 계수 증가만 확인한다.
  미증가는 조회 구간에서 증가를 관측하지 못했다는 뜻이며 설비 정지 판정이 아니다.
  형합 결과로 작업 품번을 확정하지 않는다. 마지막 관측 시각을 별도로 표시한다.
- MES 목록은 100개씩 최대 5페이지. 페이지 사이 경과 시간 20초 확인 및 요청별 timeout을 적용한다.
  공통 토큰 발급의 timeout은 기존 연동 정책을 따른다.
- 성공한 정제 MES 목록만 60초 캐시하고 계획은 다시 읽는다. 실패는 캐시하지 않는다.
- 화면 진입·날짜 변경·수동 새로고침으로 조회한다. polling/focus/reconnect/retry는 사용하지 않는다.
- 토큰은 새 목록 요청의 `access_token` 헤더에만 넣고, 원본 JSON·원본 오류·작업자 이름을 응답하지 않는다.

## 대표 사례와 검증

`frontend/tests/fixtures/mes-task-reconciliation.json`은 순수 백엔드 판정 결과로 만든 합성 데이터다.
1호기 단일 계획 일치, 2호기 같은 품번의 중복 작업, 3호기 오래된 계획 밖 작업,
4호기 일시정지 작업, 5호기 열린 작업 없음, 10호기 서로 다른 순서의 동시생산,
17호기 계획 미입력 사례를 포함한다.

실행 명령:

```sh
PYTHONPATH=backend python -m unittest production.test_mes_task_reconciliation
node --experimental-strip-types --test frontend/tests/mes-task-reconciliation.test.ts
python scripts/check-mes-task-reconciliation.py
cd frontend
npm run build
```

사용자 승인 후 Python 의존성을 설치했다. 순수 판정·리더와 Django 권한·캐시·로컬 DB
계획 변경 및 공식 목록 응답 구조를 포함한 테스트 40개, Node view-model 테스트 6개가 통과했다.
프레임워크 테스트는 별도 Django 설정, 메모리 SQLite, 외부 HTTP 차단을 사용했다.
변경 Python 파일의 문법 검사와 `git diff --check`도 통과했다.

이전 클라우드 채팅 「개발 방향 재검토」의 완료된 파일 패치 기록에서 구현을 복구했다.
패치의 원래 행 위치와 문맥을 확인해 재적용했고 합성 픽스처 생성도 복구했다.
2026-10-08 재개 환경에서 공식 SheetJS URL이 HTTP 200으로 응답했으며,
원본 package.json과 lockfile 그대로 `npm ci --no-fund --no-audit`가 성공했다(535개 패키지).
설치된 `xlsx` 버전은 0.20.3이다. 한국어·중국어·LOT·수량을 담은 XLSX 생성/재읽기를 검증했다.
복구된 전체 앱의 `npm run build`가 통과했다(TypeScript, Vite 현대/레거시 JS,
레거시 CSS, 빌드 정보). 큰 번들에 대한 Vite 경고는 남아 있다.

공개 [목록 API 공식 문서](https://v3-ali-openapi.blacklake.cn/static/api-docs-md/1681109889053785.md)도
재개 환경에서 조회했다. `taskStatus.code`와 `progressReportOpenVO.materialInfo.baseInfo.code`,
`progressReportOpenVO.plannedAmount/alreadyReportedAmount`, `Amount.unit.id`를 읽도록 리더를 보완했다.
기존 평면 응답도 수용하지만, 문서상 중첩 물료 구조가 있으면 충돌하는 평면 품번으로 대체하지 않는다.
목록 문서에 없는 입고 수량은 null이며 보고 수량으로 대체하지 않는다.
공식 문서 확인과 실제 WJ 응답·앱 조회 권한·설비 연결 검증은 별도 사실이다.

전체 앱의 `/production`을 Chromium으로 열고 저장소의 합성 API 픽스처로
한국어 데스크톱·중국어 모바일을 확인했다. 브라우저에서도 최종 SheetJS 번들의
XLSX 생성/재읽기를 수행했다. 17개 호기 행, 키보드 필터, 수동 갱신, focus 자동 갱신 방지,
쓰기 버튼 부재, 실패 시 이전 판정 숨김, 부분 응답의 요약 보류, 빈 작업 목록을 검증했다.
대시보드 grid 안의 모바일 패널이 표 최소 너비만큼 늘어나던 문제를
패널의 `min-width: 0`으로 수정해 표 내부에서 가로 스크롤되도록 했다.
검증은 합성 데이터와 로컬 정적 서버에서만 수행했으며 운영 MES/DB에 연결하지 않았다.

## 배포 전 남은 조건

1. **실제 WJ 응답 확인:** 공식 목록 문서를 조회하고 문서상 중첩 구조를 수용했으나,
   WJ의 비식별 실제 응답 표본 및 앱 조회 권한은 아직 확인하지 않았다.
   인계서의 `codex/inspection-resume-20261008` 브랜치는 원격에 없다.
   `equipments[].name`과 입고 수량의 실제 제공 여부는 표본으로 확인해야 한다.
   미지원 필드는 추측으로 보완하지 않는다.
   필수 식별 정보가 없으면 보류, 수량·개시 시각이 없으면 null이다.
2. **설비 필드가 없는 목록:** 현재는 미연결 작업으로 분리하고 판정을 보류한다.
   공식 설비 ID 매핑이 확보되면 `equipmentIdList` 조회를 추가할 수 있다.
   설비 코드의 숫자를 설비 ID나 호기로 대체하지 않는다.
3. **검증 결과 보존:** 원래 lockfile 설치와 전체 build/legacy build, 오프라인 백엔드
   및 프런트 판정 검증이 통과했다. 이는 운영 배포·실제 MES 연결 검증을 의미하지 않는다.
4. **현장 확인:** 대표 호기의 계획 일치·중복 작업·동시생산·계획 변경 사례를 담당자가 확인한다.
   한 작업의 실제 연결이 설명되고 잘못된 후보가 식별되는지 기록한다.
5. **다음 단계:** 暂停/继续의 앱 권한·조작 사유·운영 책임자를 확인한 후, 실행 전후 조회와 감사 기록을
   별도 범위로 구현한다. 실제 시범 조치는 지정 작업과 승인이 필요하다.
