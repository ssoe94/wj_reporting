# 사출 현장·실적·모니터링 정리

검토 기준: `fd92316` 이후 사출 업무 개선. 운영 데이터의 확정 결산 보고서가 아니라 코드·API 계약과 화면 연결을 검토한 개발 인수 문서다. 실제 생산 수량, 계정, 인증 정보, 운영 데이터 사본은 포함하지 않는다.

## 화면별 책임

| 화면 | 주요 사용자와 질문 | 이번 구성 |
| --- | --- | --- |
| `/field/imm01` ~ `imm17` | 현장: 지금 어떤 작업을 하고 무엇을 신고할 것인가? | 현재 업무일 입력 유지. 권한 있는 사용자가 동일 설비·업무일의 현장 기록과 계측으로 이동 |
| `/injection/dashboard#overview` | 관리자: 계획 대비 관측 실적과 확인할 원천은 무엇인가? | MES·계획 기반 개요, 현장 저장 현황, 설비별 조회 연결 |
| `#field-records` | 현장/품질: 어느 설비에서 무엇을 신고했는가? | 저장 구간, 불량 유형, 미기록/유효한 0 구분, 원천 상태가 포함된 CSV |
| `#records` | 보고 담당: 별도로 작성한 일보는 무엇인가? | 선택 날짜·설비의 수기일보 요약·전체 페이지 상세·CSV. 신규 입력은 접어서 구분 |
| `#console` | 관리자: 계획별 실행 기록을 보완해야 하는가? | 기존 실행 입력 기능 유지. 미저장 작성 대상과 새 조회 대상을 구분 |
| `#cycle-time` | 설비 담당: 현재 C/T 기준을 관리해야 하는가? | 전체 설비의 현재 설정이며 과거 조회 필터와 별개임을 명시 |
| `/mes/monitoring` | 설비 담당: 어느 시간대의 계측 신호를 확인해야 하는가? | 같은 날짜·설비로 시간대 계측 조회, 수집 상태와 미관측 구간, 선택일 MES 보고 원장 연결 |

공통 조회 링크는 `?date=YYYY-MM-DD&machine=1..17`을 사용한다. 날짜는 Asia/Shanghai 08:00부터 다음 날 08:00까지의 업무일이다. 역사 조회에서 현장 입력으로 이동하는 링크는 **현재 현장**임을 명시하고 과거 날짜를 입력 화면에 전달하지 않는다. `/injection`, `/injection/new`의 기존 조회 조건과 `#new` 입력 진입을 유지한다. 구형 `/injection/monitoring`은 30일 격자·원시 구간 조회·백필 기능이 있어 삭제하지 않았다.

| --- | --- | --- |
| MES + 생산계획 | 누적 형합 계수의 증가량(shot) × 계획 Cavity(ea/shot), 계획 순서 배분 | 계획에 배분한 추정 실적. 검사 확정 양품이 아니다. 무계획 가동의 호환성 0은 환산 불가이며 화면·CSV에서 미확정 처리 |
| `field-defects.v1` | 설비·업무일·event key·계획/순번·저장 구간, 신고 불량 ea | 저장한 구간만 나타낸다. 검사 수량과 교대 완료 기준이 없어 불량률/완료율을 계산하지 않는다. MES 또는 일보에 가산하지 않는다 |
| `InjectionReport` | 별도 수기일보, 날짜·설비·품번·작업시간·등록 수량 | 기존 보고 이력. 현장 체크포인트와 자동 연결되지 않는다. CSV upsert의 날짜·설비·품번 키로 복수 교대/교체 구간을 구분할 수 없다 |
| `ProductionExecution` | 생산계획 행에 연결한 관리자 실행·불량·메모 | 계획 실행 보완 기록. 현장 신고·수기일보와 중복 판정할 수 있는 공통 확정 키가 없다 |

## 이번에 바로잡은 판단 오류

- 수기일보의 날짜·설비가 목록에만 적용되고 요약/CSV에는 적용되지 않던 범위를 일치시켰다. 페이지네이션 전체를 조회하며 다른 날짜·설비 응답과 잘못된 응답을 거부한다.
- 원천 조회 실패와 정상 빈 응답을 구분한다. 실패 중 남아 있는 캐시는 최신 확정값으로 판단하거나 내보내지 않는다.
- canonical에서 설비별 `latest_capacity_time`, `capacity_data_available`, `data_warning`과 계획 설비 수집 완전성 정보를 overview까지 보존한다. 전체 원천이 정상이어도 개별 설비 미수집을 0으로 표시하지 않는다.
- 계획 없는 설비의 ea 환산을 보류한다. 전체 계획 설비 중 누락/지연이 있으면 합계·달성 판단을 보류하고, 관측 가능한 개별 설비는 자체 근거로 조회한다.
- 모니터링 계수 증가량 계산을 canonical reset 정책과 공유한다. 정상 증가, 큰 감소(이전 값의 20% 이하로 초기화된 경우 현재 값부터 집계), 작은 감소(증가량 0)를 구분한다. 최초 값에 기준 계수가 없으면 전체 누적값을 해당 구간 생산으로 가산하지 않는다.
- 원시 계수로 확인된 0을 과거 저장 집계가 덮어쓰지 않는다. 조회 범위에 완전히 포함된 저장 버킷만 보충한다. 음수 계수를 배제한다.
- `generated_at`(응답 생성)과 원천 최신 시각·조회 시간 범위를 분리한다. 저장 집계의 과거 계산 버전은 미확정으로 표시한다.
- 새 화면은 필요한 탭과 부가 보고를 열 때 조회한다. 빈 화면을 꾸미는 가상 KPI, 고정 OEE, 검사 분모 없는 불량률은 추가하지 않았다.

## 남은 데이터 수집·통합 순서

1. **공통 생산 구간 ID와 확정 관계**: 설비·업무일·교대·계획 ID/순번·품번·금형·시작/종료 시각을 한 구간에 연결한다. 현장 event key와 수기/실행 행은 이 구간을 참조하되, 자동 덮어쓰기 전에 원본/수정/승인 관계를 보존한다.
2. **검사 분모와 처분**: 검사 수량, 1차 양품, 불량, 재작업 투입/회수, 폐기, 미검사 수량을 수집한다. 생산량과 검사량의 대상 구간이 같을 때만 불량률을 계산한다. 현재 수기 개별/요약 불량률 분모도 함께 정리해야 한다.
3. **실제 가동 계획과 정지 구간**: 교대 캘린더, 계획 휴식/보전, 비계획 정지 시작/종료, 현장 사유 코드, 승인 상태. 계측 공백과 실제 정지를 분리한 뒤 가동률과 손실 시간을 산출한다.
4. **변경 시점 기준정보**: 금형, Cavity 변경/막힘, 기준 C/T, 재료 LOT의 적용 시작/종료. 현재 기준값을 과거 생산에 소급 적용하지 않는다.
5. **수집 품질·집계 버전**: 설비별 샘플 주기, 결측 구간, 기준 계수 유무, reset 판정, 중복/지연 수신, 계산 버전과 재집계 범위를 보존한다. 정상 관측 0과 공백을 계속 구분한다.
6. **마감 및 대사**: 현장 신고 → 관리자 검토 → 교대/업무일 확정 → MES/일보 대사 순서와 담당자를 정한다. 차이는 총계 하나 대신 미검사·재작업·환산 미확정·입력 누락·중복 후보로 분류한다.

원시 계수의 최근 보관 기간 이후에는 저장 집계를 사용할 수 있으나 기존 저장 버킷에는 계산 버전이 없다. 원시 matrix의 샘플 시점 귀속과 저장 writer의 샘플 사이 비례 배분도 서로 다르다. 이번 변경은 운영 이력 재생성이나 DB 마이그레이션을 수행하지 않는다. 전력량의 기존 단조 계수 정책은 형합 reset 정책과 별개다. 정확한 일일 ea 수량은 계획/MES canonical을 사용하고 시간대 모니터링 합계를 확정 일보로 대체하지 않는다.

## 재현·인수

- 프런트: `npm --prefix frontend run lint`, `npm --prefix frontend run build`, `node --experimental-strip-types --test frontend/tests/*.test.ts`.
- 백엔드: CI의 `python manage.py test --no-input`. 신규 회귀는 `analytics.test_field_operations`, `injection.test_report_scope`, `injection.test_counter_contract`, production의 설비 capacity evidence 테스트에서 발견한다.
- 로컬 조회 검증은 별도 loopback 서버의 저장된 읽기 응답/명시적인 합성 fixture를 사용한다. 쓰기는 거부하며 운영 생산 데이터로 해석하지 않는다.
- 브라우저 확인: 날짜·설비 링크 왕복, 미기록 vs 신고 0, 실패 안내/내보내기 중지, 수기 `#new`, 한·중 문구, 작은 화면.
- 주 개발 장비에서는 이 PR이 main에 반영된 뒤 fast-forward로 이어받는다. 공통 구간 ID와 검사 분모 설계부터 다음 개발을 이어갈 수 있다.
